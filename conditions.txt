1. METEOROLOGICAL INGESTION & LIVE WEATHER MAPPINGS
================================================================================
SafeShift integrates live meteorological feeds from Open-Meteo Meteorological 
API (Keyless & Real-time) and OpenWeatherMap API with regional fallback data.

Parameters Tracked per Hazard Zone:
- Rainfall Accumulation (24-hour total mm) [R]
- Current Rain Intensity (1-hour rate mm/h) [R_1h]
- Relative Humidity (%) [H]
- Ambient Temperature (°C) [T]
- WMO Atmospheric Condition Code (0 - 99)

WMO Weather Code Classification:
  - 0: Clear sky
  - 1-3: Mainly clear / Partly cloudy / Overcast
  - 45, 48: Foggy / Depositing rime fog
  - 51, 53, 55: Light / Moderate / Dense Drizzle
  - 61, 63, 65: Slight / Moderate / Heavy Rain
  - 66, 67: Freezing Rain
  - 71, 73, 75: Snowfall (High altitude)
  - 80, 81, 82: Slight / Moderate / Violent Rain Showers
  - 95, 96, 99: Thunderstorm / Severe Hailstorm

| R < 64.5 mm               | LOW            | monitoring      | 1              | Green Alert (Light/Moderate Rain)|

* Alert Trigger: When R >= 115.6mm and baseline risk was not High:

3. DYNAMIC FLOOD SPREAD & POLYGON INUNDATION MODEL
================================================================================
The Scenario Intelligence Engine projects physical flood spread along a continuous
timeline t in [0, 60 minutes].

Let:
  t in [0, 60] = Elapsed forecast time in minutes
  t_norm = t / 60.0 (Normalized timeline factor in [0.0, 1.0])
  R = 24-hour rainfall accumulation in mm
  Pop_0 = Baseline affected population in zone

Equations:
1. Rainfall Amplification Factor:
   RainFactor = max(1.0, 1.0 + (R / 110.0))

2. Polygon Perimeter Dilation / Buffer Factor (E_flood):
   E_flood(t) = 1.0 + (RainFactor - 1.0) * (0.15 + 0.85 * t_norm)

   * Geometric Dilation: Buffered in degrees using Shapely:
     BufferDegrees = (E_flood(t) - 1.0) * 0.05
     BufferedPolygon = Polygon.buffer(BufferDegrees)

3. Projected Inundation Depth (Depth_m):
   Depth_m(t) = 0.4 + (R / 45.0) * (0.2 + 0.8 * t_norm) [meters]

4. Population Displacement Surge:
   Pop(t) = Pop_0 * [1.0 + (E_flood(t) - 1.0) * 0.75]

5. Flood Spread Percentage:
   SpreadPct(t) = (E_flood(t) - 1.0) * 100.0 [%]

6. Flood Severity Index (S_flood in [0.0, 1.0]):
   S_flood = min(1.0, (R / 140.0) * 0.6 + t_norm * 0.4)

7. Dynamic Escalation Thresholds:
   - High Risk: R >= 80mm OR (R >= 50mm AND t >= 25m) OR t >= 45m
   - Medium Risk: R >= 40mm OR t >= 15m
   - Critical Alert Trigger: R >= 90mm AND t >= 30m -> Flash Inundation Cresting

4. DYNAMIC LANDSLIDE SLOPE PROBABILITY MODEL
================================================================================
Simulates hillside saturation, shear failure, and debris flow probability.

Let:
  P_0 = Base terrain vulnerability:
        P_0 = 0.25 (if Baseline Risk = Low)
        P_0 = 0.50 (if Baseline Risk = Medium)
        P_0 = 0.70 (if Baseline Risk = High)
  H = Relative Humidity (%)
  R = Rainfall accumulation (mm)
  t_norm = t / 60.0

Equations:
1. Soil Saturation Rate (S_soil):
   S_soil = (H / 100.0) * (R / 80.0)

2. Dynamic Slope Failure Probability P_landslide(t):
   P_landslide(t) = min(0.98, P_0 + S_soil * 0.35 * t_norm)

3. Hazard Zone Expansion Factor (E_landslide):
   E_landslide(t) = 1.0 + (P_landslide(t) * 0.45 * t_norm)

4. Hillside Population Displacement Surge:
   Pop(t) = Pop_0 * [1.0 + (E_landslide(t) - 1.0) * 0.60]

5. Landslide Severity Index (S_landslide in [0.0, 1.0]):
   S_landslide = P_landslide(t)

6. Landslide Risk Escalation Thresholds:
   - High Risk: P_landslide >= 0.70 OR (R >= 70mm AND t >= 20m)
   - Medium Risk: P_landslide >= 0.45 OR (R >= 40mm AND t >= 15m)
   - Critical Warning Alert: P_landslide >= 0.75 AND t >= 15m -> High Landslide Warning

6. SAFE ZONE CAPACITY & OCCUPANCY GROWTH FORECAST MODEL
================================================================================
Tracks live and projected shelter occupancy across all 18 safe shelters.

Let:
  Cap = Total shelter capacity (bed count)
  Occ_0 = Initial occupancy = Cap * [0.55 + ((idx % 4) * 0.11)] (55% to 88%)
  r_inflow = Base shelter inflow rate = 120 + ((idx * 45) % 150) [people/min]
  InflowEvacuees = Total evacuees allocated from matched hazard zones
  t in [0, 60] = Simulation timeline minutes

Equations:
1. Projected Occupancy at Time t:
   ArrivalProgress = min(1.0, (t / 60.0) * 1.2)
   Occ(t) = min(Cap, Occ_0 + (InflowEvacuees * 0.55 * ArrivalProgress) + (r_inflow * (t / 60.0) * 12))

2. Remaining Shelter Capacity:
   RemCap(t) = max(0, Cap - Occ(t))

3. Fill Percentage:
   FillPct(t) = (Occ(t) / Cap) * 100.0 [%]

4. Estimated Time to 100% Saturation (ETA_full):
   ETA_full = (RemCap(t) / r_inflow) if RemCap > 0 else 0 [minutes]

5. Multi-Tier Capacity Threshold Alerts:
--------------------------------------------------------------------------------
| Fill Percentage (FillPct) | Remaining Cap | Alert Level | Status Color | Action Mandatory               |
|---------------------------|---------------|-------------|--------------|--------------------------------|
| FillPct >= 100.0%         | 0%            | FULL        | #ef4444      | Shelter Saturated - Divert Flow|
| 90.0% <= FillPct < 100.0% | <= 10%        | CRITICAL    | #ff6b6b      | 10% Remaining - Reroute Active |
| 70.0% <= FillPct < 90.0%  | <= 30%        | WARNING     | #f59e0b      | 30% Remaining - Standby Inflow |
| FillPct < 70.0%           | > 30%         | NORMAL      | #10b981      | Optimal Shelter Capacity       |

7. MULTI-ZONE SPILLOVER REROUTING & ALTERNATE SELECTION MODEL
================================================================================
Trigger Condition: When a safe haven reaches FillPct >= 90% (only 10% remaining),
excess evacuees are rerouted to candidate safe havens.

Candidate Filtering Criteria:
  - Exclude currently overloaded safe haven.
  - Require RemCap > 0 AND FillPct < 99%.

Candidate Suitability Score (Lower score = higher ranking):
  Score(c) = (Distance_km * 0.7) - ((RemCap / 1000.0) * 0.3)

Top 2 Ranked Alternates:
  - Alternate 1 (Primary Alternate): Nearest candidate with available headroom.
  - Alternate 2 (Secondary Alternate): Contingency candidate with available headroom.

Spillover Corridor Map Rendering:
  - Color: #8b5cf6 (Purple dashed polyline)
  - Tag: "Automated Spillover Reroute"
  - Dash Pattern: '8, 6', Weight: 4.0px

8. EMERGENCY RELOCATION TRIAGE & PRIORITY SCORING MODEL
================================================================================
1. Relocation Priority Score:
   PriorityScore = RiskScore * AffectedPopulation
   Where: High Risk = 3, Medium Risk = 2, Low Risk = 1

2. Greedy Proximity Matching:
   - Hazard zones are sorted by PriorityScore in descending order.
   - For each hazard zone, safe zones are ranked by Great-Circle Haversine distance:
     d = 2 * r * asin(sqrt(sin^2((lat2 - lat1)/2) + cos(lat1)*cos(lat2)*sin^2((lon2 - lon1)/2)))
     where r = 6371.0 km.
   - People allocated: Allocated = min(PeopleRemaining, SafeZone.RemCap)
   - SafeZone.RemCap is decremented; if population exceeds capacity, split across 
     next nearest safe zone.

9. HIGHWAY NAVIGATION & ROUTING PHYSICS MODEL
================================================================================
SafeShift implements a hybrid real-world highway routing architecture combining 
OpenStreetMap/OSRM high-density waypoint geometry with mathematical transit models:

1. Real-World Turn-by-Turn Highway Ingestion (OSRM Engine):
   - Precomputed exact road geometry dataset across all 37 primary evacuation pairs.
   - Spatial density: N_waypoints in [350, 550] GPS coordinate pairs per route.
   - Route path follows actual national highways (NH-44, NH-58, NH-7, state expressways,
     mountain passes, and river bridges).
   - In-memory client cache retrieval latency: t_lookup < 1 ms.
   - Dynamic OSRM API endpoint for custom routing:
     URL: https://router.project-osrm.org/route/v1/driving/{lon1},{lat1};{lon2},{lat2}?overview=full&geometries=geojson

2. Road Curvature & Winding Factor (W):
   - Dense Himalayan / Western Ghats terrain: W = 1.35
   - Dense Urban / Congested delta: W = 1.28
   - Plain Interstate Highway: W = 1.20
   RoadDistance_km = CrowFliesDistance_km * W

3. Road Speed Profile (V):
   - Mountainous winding route: V = 42 km/h
   - Monsoon flooded urban corridor: V = 35 km/h
   - National Highway corridor: V = 65 km/h

4. Travel Duration:
   TravelTime_min = round((RoadDistance_km / V) * 60) [minutes]

5. Fallback Quadratic Bezier Highway Interpolation (for custom ad-hoc waypoints):
   Midpoint with perpendicular lateral displacement:
   dx = dest_lon - orig_lon
   dy = dest_lat - orig_lat
   Perpendicular vector: (-dy, dx) scaled by road curvature factor.

6. Visual Cartographic Polyline Layering:
   - Base Contrast Casing: Solid outer line (Weight: 9.0px, Opacity: 0.95, Color: #0f172a / #ffffff).
   - Active Navigation Polyline: Solid royal blue (Weight: 5.5px, Opacity: 1.0, Color: #2563eb).
   - Spillover Reroute Polyline: Dashed purple (Weight: 4.0px, DashArray: '8, 6', Color: #8b5cf6).
   - Alternate 1 Corridor: Emerald green (Weight: 5.5px, Color: #10b981).
   - Alternate 2 Corridor: Amber orange (Weight: 5.5px, Color: #f59e0b).

10. GOOGLE GEMINI AI SITUATIONAL INTELLIGENCE & OPERATIONAL DIRECTIVE EVALUATION MODEL
================================================================================
SafeShift synthesizes spatial relocation plans into high-level executive tactical 
briefings and operational field directives using Google Gemini AI (gemini-2.5-flash-lite / 
gemini-1.5-flash) backed by a sub-5ms deterministic expert decision engine.

1. EVALUATION MODE DIFFERENTIATION:
--------------------------------------------------------------------------------
The situational intelligence engine evaluates plans under two distinct operational paradigms:

A. LIVE REAL-TIME METEOROLOGICAL DISASTER MODE (mode = "live"):
   - Inputs: Dynamic risk levels derived from Open-Meteo live rainfall accumulation [R], 
     humidity [H], and IMD Red/Orange alert triggers.
   - Core KPI Evaluation:
     * Total Dispatched Evacuees: P_total = Σ(People_i)
     * Active High-Risk Count: N_high = Σ(1 for zone where Risk == HIGH)
     * Total Evacuation Corridors: N_corridors = len(RelocationPlan)

B. BASELINE STRUCTURAL & HISTORICAL VULNERABILITY MODE (mode = "baseline"):
   - Inputs: Intrinsic topographical vulnerability index, elevation delta, river basin 
     catchment exposure, and permanent hill slope classifications.
   - Core Focus: Strategic pre-disaster planning, infrastructure fortification, and 
     contingency safe haven capacity staging.

2. MULTI-TIER OPERATIONAL DIRECTIVE DECISION TREE:
--------------------------------------------------------------------------------
The decision engine synthesizes customized field directives based on mode and risk thresholds:

TIER A: ACTIVE METEOROLOGICAL EMERGENCIES (Live Mode AND N_high > 0):
  Triggered when live rainfall exceeds IMD Red Alert (R >= 115.6mm) or GSI Critical Slope 
  Saturation (R >= 64.5mm in mountainous terrain).
  * Executive Summary Focus: Urgent civilian relocation, imminent inundation or debris flow.
  * Sector Priority Justification: "Live meteorological telemetry escalated this zone to HIGH 
    risk due to severe precipitation exceeding IMD disaster thresholds. Critical priority score 
    mandates immediate emergency convoy routing."
  * Field Directives:
    1. Deploy immediate NDRF/SDRF evacuation convoys to active High-Risk zones before road inundation worsens.
    2. Monitor live Open-Meteo precipitation feeds for rainfall exceeding IMD Red Alert (115.6mm) thresholds.
    3. Enforce green corridors along national highways to ensure convoy travel times stay within estimated windows.
    4. Alert receiving safe havens to prepare medical triage, drinking water, and high-protein ration reserves.

TIER B: NORMAL WEATHER / STANDBY READINESS (Live Mode AND N_high == 0):
  Triggered when all monitored sectors exhibit low to moderate precipitation (R < 64.5mm).
  * Executive Summary Focus: Stable atmospheric state, 0 active catastrophic alerts, routine readiness.
  * Sector Priority Justification: "Zone is currently at LOW/MEDIUM risk with normal precipitation. 
    Routine monitoring active; no immediate evacuation required. Evacuation corridor remains 
    pre-allocated for contingency."
  * Field Directives (Prevents false alarms and premature mass panic):
    1. Maintain continuous meteorological telemetry monitoring across low-lying floodplains and steep mountain slopes.
    2. Keep designated emergency transport convoys and safe shelter intake personnel on standby readiness.
    3. Verify drainage channel clearances and slope telemetry before precipitation intensifies.
    4. Ensure emergency communication relays between district emergency operating centers (DEOC) remain active.

TIER C: BASELINE STRUCTURAL & HISTORICAL TRIAGE (Baseline Mode):
  * Executive Summary Focus: Permanent terrain exposure, low-elevation river catchments, and 
    long-term demographic vulnerability.
  * Sector Priority Justification: "Historical baseline vulnerability index designates this zone as 
    [HIGH/MEDIUM/LOW] risk due to low-lying elevation and high exposure, requiring prioritized emergency clearance."
  * Field Directives:
    1. Pre-position disaster response vehicles and emergency shelters in proximity to high-vulnerability sectors.
    2. Review structural flood defenses and slope reinforcement assets across baseline high-risk corridors.
    3. Verify safe haven bed capacity readiness (maintaining >10% emergency reserve headroom).
    4. Switch to 'Live Weather Mode' to incorporate real-time precipitation and dynamic risk surges.

3. IN-MEMORY CACHE FORMULATION & LATENCY GUARANTEE:
--------------------------------------------------------------------------------
To prevent API rate-limiting and ensure zero-lag transitions (<1ms) when switching 
between live weather and baseline views on the command dashboard:

  Cache Key: k = f"{mode}_{P_total}_{N_high}"
  Cache TTL: 300 seconds (5 minutes)

  If now - Cache[k].timestamp < TTL:
      return Cache[k].data (Instantaneous retrieval: < 1ms)
  Else:
      Execute Gemini LLM request (Timeout: 1.8s) -> Fallback to Rule Engine (< 5ms) on timeout/error.

4. CLEAN TYPOGRAPHY & ZERO-EMOJI NDMA STANDARD:
--------------------------------------------------------------------------------
All situational summaries, sector reasons, and operational directives are enforced to follow 
formal National Disaster Management Authority (NDMA) reporting standards without emojis or 
informal symbols.

11. END-TO-END APPLICATION RUNTIME WORKFLOW
================================================================================
This section describes the flow implemented by the current frontend and backend. Where
marketing copy, this reference, and runtime code differ, the implementation is authoritative.

A. BROWSER STARTUP AND FALLBACK STATE:
--------------------------------------------------------------------------------
1. Vite serves frontend/index.html, which loads frontend/src/main.jsx. React mounts
   frontend/src/App.jsx under StrictMode.
2. App.jsx imports frontend/src/data/hazard_zones.json and
   frontend/src/data/initial_highway_routes.json. geoUtils.js derives centroids,
   client-side demographic/capacity estimates, an initial baseline relocation plan,
   and initial safe-zone occupancy so the app can render before the API responds.
3. The initial view is the landing page. Launch Command Center switches directly to
   the operational workspace, initially on the GIS map.
4. On mount, App.jsx requests /zones/live, /weather-impact, /relocation-plan, and
   /safezones/status. Most requests have a 2.5-second timeout. The UI remains usable
   when the backend is unavailable by retaining bundled data and using browser-side
   weather, relocation, route, and capacity fallbacks.
5. The app polls /safezones/status?auto_tick=true every 4 seconds. Successful backend
   requests advance the in-memory occupancy simulation. If the request fails, the
   browser applies a small synthetic fill change. Core zone/weather requests refresh
   on a 10-minute interval; weather service cache TTL is also 10 minutes.

B. BACKEND DATA AND LIVE WEATHER:
--------------------------------------------------------------------------------
1. backend/main.py loads GeoJSON at process startup, searching backend/data and
   repository-level data locations, then initializes safezone_manager from it.
   The browser's bundled GeoJSON is an independent startup fallback.
2. /zones/live and /weather-impact call get_live_zones_with_weather in
   backend/weather_service.py. A warm cache is returned immediately. On cold start,
   deterministic fallback weather is assembled and a background refresh begins.
3. The zone refresh uses batched Open-Meteo requests. Failed/incomplete fetches use
   geographic fallback weather. The single-coordinate weather helper can use
   OpenWeatherMap when configured, then Open-Meteo, then fallback; the batch zone
   refresh path uses Open-Meteo and fallback.
4. Zone features are enriched with weather, centroids, population demographics,
   and safe-zone capacities. backend/population_service.py estimates resident
   population from geometry, estimates visitor capacity using OpenStreetMap Overpass
   accommodation data where available, and applies time/season occupancy factors.
   Safe-zone capacity is estimated from polygon area and the 3.5 m2-per-person rule,
   subject to configured minimum and maximum values.
5. For hazards, predict_risk classifies live risk from rainfall: floods use 64.5 mm
   and 115.6 mm thresholds; landslides use 35.5 mm and 64.5 mm thresholds. The prior
   risk is retained as baseline_risk, risk is set to the live result, and escalation
   alerts are attached to weather metadata.

C. RELOCATION PLAN AND ROUTE METRICS:
--------------------------------------------------------------------------------
1. /relocation-plan?live=true uses weather-enriched GeoJSON; live=false uses base
   GeoJSON. Both call generate_relocation_plan in backend/relocation.py.
2. The planner separates hazard and safe features, calculates polygon centroids,
   and sorts hazards by descending risk_score * population (3/2/1 for high/medium/low).
3. In that priority order, each hazard ranks shelters by great-circle Haversine
   distance and allocates evacuees to available capacity. An origin can split over
   several shelters; any remainder is returned as an unassigned overflow row.
4. Plan distance/time values come from backend/routing.py's simple road-metrics
   model (Haversine distance multiplied by 1.25, then 50 km/h). This is separate
   from detailed route geometry.
5. Detailed backend geometry checks the precomputed route cache, optional
   OpenRouteService, public OSRM, then a curved interpolation fallback. The browser
   also bundles route geometry and calls OSRM directly if a local route is missing
   or sparse. Displaying a route does not validate live road closures.

D. SHELTER CAPACITY, AI, AND SCENARIO SERVICES:
--------------------------------------------------------------------------------
1. backend/safezone_service.py stores occupancy in a process-local in-memory manager.
   It calculates occupancy, remaining capacity, estimated time-to-full, and alerts
   at 70%, 90%, and 100%. /safezones/update can tick or reset this state.
2. Alternate safe havens exclude the current shelter, require available capacity
   where possible, and are ranked by road-distance and remaining-capacity score.
   /safezones/multi-routes packages a primary route and up to two alternate routes.
3. /ai-explain builds a plan for baseline/live mode and calls
   backend/gemini_explainer.py. Gemini is optional; the service caches responses
   for five minutes and returns a deterministic rule-based briefing when the key,
   provider, or request is unavailable.
4. /simulate-disaster invokes backend/simulation.py for a 0-60 minute projection.
   It enriches live weather, dilates flood polygons, estimates landslide probability,
   recomputes relocations, projects shelter loading, and returns alerts and spillover
   recommendations. The endpoint exists, but the current React app does not call it.

12. OPERATOR WORKFLOWS
================================================================================
A. MAP AND RISK REVIEW:
--------------------------------------------------------------------------------
1. Open GIS Map View or Split Command View.
2. Choose Baseline Vulnerability or Live Weather Risk. The app requests a matching
   relocation plan; risk colors, statistics, alerts, and table labels follow the
   selected mode. Live weather zone data is loaded independently during refresh.
3. Toggle filter chips to show all zones or selected risk, hazard, and safe-zone
   layers. Selecting a polygon opens ZoneDetailsModal with risk, population,
   demographics, weather, shelter matches, and route actions.
4. If rainfall is absent on the selected zone, the details panel can request
   browser-side Open-Meteo weather and update the zone in app state.
5. Locate/Inspect actions select the feature, switch from dashboard/capacity to the
   map when needed, and zoom to its polygon or centroid.

B. REVIEW THE RELOCATION PLAN AND TRACE A ROUTE:
--------------------------------------------------------------------------------
1. Open Analytics & Relocation for KPIs, charts, and the searchable/filterable
   RelocationTable, or use the dashboard portion of Split Command View.
2. Trace from a table row or zone detail resolves origin/destination coordinates,
   checks bundled geometry and the in-memory cache, draws an immediate local route,
   then may replace it with a live OSRM route.
3. The map fits the route bounds. Escape clears the detailed or multi-route overlay.

C. MONITOR SHELTERS AND COMPARE ALTERNATES:
--------------------------------------------------------------------------------
1. Open Shelter Capacities to review occupancy, available beds, projected fill,
   status alerts, and active relocation rows. GeoJSON-derived values are used if
   live capacity status is unavailable.
2. The page can compute display-level automatic destination changes when the
   assigned shelter is at least 90% full and auto-rerouting is enabled. Its row
   alternate dropdown stores manual reroutes in page-local state and can trace the
   selected route.
3. View Alternate Routes first builds a client-side comparison, then requests
   /safezones/multi-routes for backend geometry and capacity information.
4. Confirm & Activate Route draws the selected corridor and updates matching rows
   in App.jsx relocation-plan state. This is distinct from the capacity page's
   local dropdown reroute state.
5. Reset Simulation posts { "reset": true } to /safezones/update. If the API fails,
   the browser restores its initial client-side capacity estimate.
6. Capacity toasts expose alternate-route and locate actions. The smart weather
   alert banner derives alerts from weather metadata and current zone properties.

D. GENERATE AN OPERATIONAL BRIEFING:
--------------------------------------------------------------------------------
1. Open AI Briefing from the operations header.
2. The modal renders an immediate local briefing from the current plan, then
   requests /ai-explain for the active risk mode.
3. Switching Baseline/Live updates app risk mode and requests another briefing.
   Regenerate repeats the request; backend fallback behavior is described in
   Section 11.D.

  The backend simulator is callable independently, but its projection is not applied
  to the frontend map, relocation plan, or timeline controls.
- Safe-zone occupancy is process-local memory. It resets on backend restart and is
  not shared across multiple workers/instances.

IMPLEMENTATION ALIGNMENT NOTES:
- backend/relocation.py implements greedy priority-ordered nearest-capacity matching;
  it does not invoke SciPy or solve a linear program, despite LP claims elsewhere.
- Detailed route geometry is not proof of current road status or closure avoidance.
- /safezones/multi-routes uses backend route geometry, while ordinary plan tracing
  currently uses client-side cached geometry and direct browser OSRM.

14. LOCAL DEVELOPMENT, DEPLOYMENT & DATA MAINTENANCE

LOCAL DEVELOPMENT (run backend and frontend in separate terminals from repository root):

Backend:
  cd backend
  ..\venv\Scripts\Activate.ps1
  python -m uvicorn main:app --host 127.0.0.1 --port 8005 --reload

Frontend:
  cd frontend
  npm install
  npm run dev

The Vite server is configured for port 3000. Frontend API base defaults to
http://127.0.0.1:8005; set VITE_API_BASE_URL to target another backend. Backend
optional integrations are configured in backend/.env: GEMINI_API_KEY,
OPENROUTESERVICE_API_KEY, and optionally OPENWEATHERMAP_API_KEY.

Useful frontend checks from frontend/:
  npm run lint
  npm run build

DEPLOYMENT AND DATA MAINTENANCE:
- Root vercel.json and frontend/vercel.json build the Vite frontend. Set
  VITE_API_BASE_URL in Vercel to the deployed API; localhost is for local use only.
- render.yaml configures the FastAPI service rooted at backend/. Its current
  startCommand ends with "--port " but has no port value; verify it before relying
  on Render deployment.
- Backend and frontend GeoJSON are separate copies: backend/data/hazard_zones.geojson
  and frontend/src/data/hazard_zones.json. Keep them aligned when editing zones.
- backend/generate_all_india_data.py writes to a developer-specific absolute Windows
  path. Check/update that output path before using it in another environment.
- backend/precompute.py expects to run from repository root, reads data/hazard_zones.geojson,
  and writes data/precomputed_routes.json. Verify routing sources before generating.
- The backend has no test command configured in project metadata. Use implementation
  files as the source of runtime truth when documented claims and code differ.
